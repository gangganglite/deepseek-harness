## 历史评审记录

## 本轮复评结论 · 有条件通过

按 [PRD AC-1 至 AC-8](../spec/PRD.md#验收条件) 和[最新方案](../design/TECH_DESIGN.md)复评，仓库基线 `f607b270c5`。采用 Harness 同批并行执行、Jobs 托管和持续写文件的方向可保留。无新 P0。实施负责人需要落实下列两项条件，并用实际 profile 验证。PRD 的 AC-7 仍需同步已明确的运行中续读时序。

### P1 · 用实际 profile 确认 B 能执行，并区分执行与结果发布

方案第 36 行已经给出并行声明、至少两个槽位和在工具执行体内等待专项审批。此前的独占调度冲突已经解决。现有 [`batch.ts` 的准备阶段](../../../packages/core/tools/src/batch.ts#L154)仍按模型调用顺序等待，且[通用前置审批](../../../packages/core/tools/src/pipeline.ts#L201)发生在准备阶段。如果实际 profile 对 A 在此阶段提出审批，B 仍不会开始。实施负责人应确定首版使用的 profile 及审批归属，用真实策略验证通用拒绝仍有效，并确保 A 的等待发生在专项执行阶段。

即使 B 先执行完，[批处理按模型调用顺序提交结果](../../../packages/core/tools/src/batch.ts#L138)。测试应在 A 等待期间观察 B 的远端命令已经完成，并在 A 获批后检查两条工具结果。该设计不应承诺模型提前收到 B 的结果。用户要求的独立执行可沿现有调度实现。

### P1 · 运行中路径与完整文件元数据需要不同发布时机

方案第 42 至 46 行采用流式写入，解决了整段字符串采集上限妨碍保存完整输出的问题。初次响应单独返回路径和作业 ID 的方向合适。现有 [`JobOutputSource.spillPath`](../../../packages/jobs/jobs/src/types.ts#L100) 表示完整输出文件，[作业输出渲染](../../../packages/jobs/tool-jobs/src/render.ts#L75)在内存输出丢失时会直接将它称为完整输出。若正在写或写入失败的路径也放进该字段，模型会同时收到相互冲突的状态。

实施负责人应在首个工具响应中用带状态的提示返回可增长文件路径。完整写入、关闭成功后，再通过作业输出源发布 `spillPath`，并由现有作业末次采集把元数据带入终态。失败或取消时，已发布的早返回路径仅代表部分输出，不进入完整文件字段。还需指定文件所有者和保留机制。[`jobs-local` 移除记录](../../../packages/jobs/jobs-local/src/index.ts#L670)只处理作业状态，不能替代对另行创建文件的清理。测试覆盖运行中读到当时 EOF、环丢数据、终态全文读回、失败后状态以及保留范围。文件读取应使用实际 Harness 会话验证。

## 历史复评记录

## 复评结论 · 需要修改

按 [PRD AC-1 至 AC-8](../spec/PRD.md#验收条件) 复评更新后的[技术方案](../design/TECH_DESIGN.md)，仓库基线 `f607b270c5`。此前的输出脱敏、路径覆盖和目标切换三项发现已按最新需求重新判定。未发现新的 P0。当前有两项 P1，涉及 AC-8 的真实调度和 AC-7 的完整文件交付。

### P1 · A 等审批时，现有工具调度会阻塞同批的 B

技术方案第 31 行允许审批等待期间操作另一目标，第 68 行却明确工具不声明并发安全。[`executionMode`](../../../packages/core/tools/src/pipeline.ts#L106) 将缺少声明的工具归为独占。[`batch.ts`](../../../packages/core/tools/src/batch.ts#L76) 对独占调用只执行该调用并等待结束，才处理下一调用。模型同批提交 A 和 B 时，A 等审批，B 无法开始。按目标独立登记会话只能固定命令路由，无法改变调度规则。该冲突由静态调用链确认，尚未运行真实 profile。

修订方案时明确 AC-8 的调度前提。若使用同批并行，先确定远端工具在哪些调用条件下可安全标为并发，如何处理同目标并发及多个审批请求，并明确组成 profile 的并行槽位要求。用实际 Harness 工具批次同时提交 A、B，在 A 未批准时观察 B 完成，再批准 A 并确认其原连接收到命令。保留原连接关闭与调用取消的反例。

### P1 · 原始采集达到字节上限时，成功命令也可能没有完整文件

技术方案第 38 行选用了整段字符串 `saveText`，达到采集字节上限就放弃发布完整文件。[现有本机实现](../../../packages/spill/spill-local/src/index.ts#L150) 确实接收完整文本后才持久化。只要输出超过该字节上限，磁盘仍可用且命令正常结束，按现设计也可能只有预览。这和 AC-7 对超限输出提供完整文件的行为有差距。存储失败的反馈规则仍然适用。

优先验证能否使用当前会话可读的文件，将溢出内容顺序写入并在完成后发布路径，同时在内存保留 3000 字预览。如果需要保留采集字节硬上限并允许放弃完整文件，须先明确该产品行为。验证正常命令输出超过拟议采集上限并全文读回，同时覆盖超时、写入失败及未完成文件的状态。

## 发现

### P0 · 远端输出过滤缺少可执行的保密规则

[方案第 31 行](../design/TECH_DESIGN.md#认证会话归属与失败)同时规定限长收集与按认证值过滤。若原始采集先到上限，落在边界上的认证值只剩前缀，完整字面值匹配无法剔除它。工具参数或 stdout、stderr 的不同呈现路径也需要明确归属。该缺口影响 AC-2，涉及模型请求及持久化结果。

修订时定义进入工具响应前的统一释放规则。说明流式或有界缓冲如何处理跨块、编码和采集边界，以及无法安全处理的响应如何丢弃。认证错误继续使用独立的固定投影。用合成哨兵测试完整值、跨块、恰逢采集上限、两类标准流与失败结果，并核对 Session。把范围限定为本地认证材料及其已知回显。任意远端应用数据是否包含其他敏感值需另行界定。

### P1 · 路径通过结构校验之后仍缺少 profile 级写入授权

[方案第 21 至 23 行](../design/TECH_DESIGN.md#路径发现与更新)用受信目录、只读校验和写入锁保护路径。伪代码中的 `setPath` 只有校验和提交。只读验证能识别格式，无法判断当前调用者是否能改变其他会话后续使用的 profile 数据源。这条调用的路径参数还要经过 Harness 工具执行记录，固定错误与脱敏结果只能保护返回方向。

区分自动保存与显式变更。把自动保存限制在 profile 已信任且唯一的来源。为显式写入明确采用 Host 或现有 Harness 审批的授权方式，在写入前绑定候选文件及当前配置版本，并明确哪些路径可出现在工具参数和记录中。补充有权更新、无权拒绝、验证后被替换和跨会话观察旧值的用例，覆盖 AC-3 和 AC-5。

### P1 · 会话切换和收尾缺少确定的提交规则

[方案第 30 至 31 行及伪代码](../design/TECH_DESIGN.md#供评审的代码设计)规定重新审批、按调用范围串行建连，并在 turn 结束后释放，但未说明切换失败时旧会话如何处理，以及命令开始与卸载或断线如何协调。特别是命令审批期间会话可被替换。`requireSameLiveSession` 与真正打开远端通道之间若发生异步切换，单独检查一次不足以固定目标和结果归属。

补一张会话状态表或等价伪代码，明确 turn 的来源及可订阅的结束事件，规定切换失败时旧会话的状态、会话替换与通道打开的串行范围，以及由谁关闭并等待在途通道。在真实工具执行路径验证审批期间切换、切换失败、卸载和调用取消。断线后的未知结果保持可见，覆盖 AC-4 和 AC-6。

## 实施前待验证

- 先验证密码和私钥各一条使用 XTerminal 正常本机读取方式的端到端样例。真实库字段存在仅确认格式线索。合成记录可以验证 SSH 路径、主机身份与保密性，不能替代对实际 XTerminal 存储编码和解锁能力的验证。验证只使用明确授权的测试目标，记录脱敏状态。
- 用隔离 SSH 服务和真实 Cordis 配置跑一次从任务到命令结果的闭环。现有审批服务以 `allowed-once` 为唯一批准，`never` 策略下请求会被拒绝。验证目标和命令审批的真实呈现，包含没有审批通道时的失败。早期仅查询验证继续用于 AC-1。
- 已执行静态接口核对和合成字面值边界探针。探针确认原始采集先截断时，完整值替换会留下认证值前缀。该结果针对设计反例，尚无新插件实现可运行验证。

## 历史评审 · 只读查询

结论为通过实施。用户提供了获取连接信息的路径，查询所需三个字段可在 SQLite 内投影，插件无需读取或传递认证字段，也无需复用启动远程 Helper 的 `dsh-ssh` 服务。

评审要求用带凭据哨兵的记录验证完整工具结果，使用损坏数据库验证固定错误文本，确认部署配置与模型参数之间不存在文件路径透传。需保留最小权限提示，服务器标题是可见标签，调用方应仅在允许模型查看该清单的本机配置中启用。

真实库仅核对了表和字段类型，实际查询、Cordis 接入和回放证据由实施阶段补齐。
